# Private course cache

CourseCache stores opt-in search snapshots and derived indexes.
An integrating caller must explicitly enable it and provide an authorization
callback that checks the current account and course access before each read, write, inspect and delete operation. Only an explicit true grants access. A failed authorization check returns a fixed error without upstream details.
Only pass supported, sanitized course text and its derived index.

The store uses the OS application data directory beside lab preferences, under
courses-mcp/course-cache. The institution and username determine the account
namespace. Local filesystem permissions protect the records. Credentials and
cookies are outside the record contract.

Schema v1 stores one JSON record per course with content and index together.
Writes use an exclusive lock and atomic replacement. Records above 1 MiB or with
unsupported schema fail validation. Timestamps must use canonical UTC ISO format,
as generated by the writer. Reads treat records aged seven days or more, future
timestamps and unverifiable clocks as misses. Expiry does not remove files from disk.

Inspect returns size, timestamp and freshness (fresh, expired, future or unknown).
These describe the local write age, not a new faculty/source verification. The
freshness field is additive; existing bytes/updatedAt remain unchanged. Delete
removes the content and index together. After Moodle access is revoked, the account owner can stop the server and remove the local record manually. Stop the server before manually recovering stale
locks or removing malformed files. Future schema changes require an explicit
migration or deletion and rebuild.

Each account can keep up to 32 course records of at most 1 MiB each. Expired
records still occupy a slot until deleted. Replacing an existing record does
not use another slot. Cache writes and deletions share an exclusive account
lock so concurrent writers cannot reserve the same remaining slot.
Set MOODLE_CACHE_SEARCH_INDEXES=1 locally to reuse an index after freshly authorized evidence matches its stored fingerprint. Moodle reads still occur. Failed cache operations fall back to the live index.
`search_courses` attempts to discard the stored course snapshot when live discovery fails or selected resources are incomplete. Searches use only current evidence in these cases, and cache deletion failures do not prevent live search.
Per-course coverage includes CACHE_INVALIDATION_FAILED if the cached snapshot could not be removed. The response still reflects current Moodle evidence.

Search coverage reports CACHE_READ_FAILED for storage read errors, CACHE_INDEX_INVALID for a matching record whose index cannot be decoded, and CACHE_WRITE_FAILED when the rebuilt index cannot be saved. These warnings describe local storage. The coverage status still reflects live Moodle evidence.

## Manage a course cache through MCP

Use get_course_cache(courseId) to inspect the stored record's size and timestamp.
The result includes enabled and a stored/empty status, with no cached text or
local path. The stored status describes presence, including expired records;
record.freshness distinguishes their usability. A stored result is not a promise
that the record can be reused. Invalid records fail validation; clear them and
rebuild rather than attempting implicit schema migration.

Use clear_course_cache(courseId) after an explicit request to clear a course's
local index. It can remove a malformed record and repeated calls are safe.
Both tools check current enrollment and remain available when search caching
is switched off. Lab preferences are stored separately.

Pass refresh=true to search_courses to rebuild from current Moodle evidence without reading the saved index. With caching enabled, a successful complete rebuild replaces the stored snapshot. The returned indexReused flag is false for that call. Normal search and forced refresh both recheck live access and read selected evidence.

## Lifecycle validation

Temporary-directory tests exercise restart reuse, exact seven-day expiry,
future/unverifiable clocks, account/institution/password changes, caller identity
mutation, revoked/failed authorization for all operations, corruption, oversized
replacements, schema/timestamp rejection, junction guards, account quota and
competing writers for the last slot. POSIX file/directory modes are checked only
on POSIX; Windows uses inherited ACLs and is not claimed to provide encryption.

A real child-process interruption test stops a writer after it holds the account
lock. The previous committed record remains readable; further writes fail busy
until explicit recovery after stopping writers. No automatic lock stealing or
crash-resume promise is made. This is interruption before atomic replacement,
not a guarantee of durability through power loss: directory fsync/native filesystem
behavior are outside this implementation's guarantees. The independent v1 security
review remains tracked separately in #48.
